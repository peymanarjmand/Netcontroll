# راهنمای پذیرش Netcontroll 2.0 روی ویندوز

این راهنما برای تأیید نسخهٔ نصب‌شده روی **Windows 10/11 x64** است. اجرای موفق تست‌های منطقی، جای آزمون رابط WPF، Chrome، Codex Desktop و مسیر واقعی شبکه روی لپ‌تاپ را نمی‌گیرد. جدول‌های این سند عمداً بدون نتیجهٔ ازپیش‌تأییدشده هستند؛ هر مورد را پس از مشاهدهٔ شواهد، «قبول»، «رد» یا «قابل‌آزمون نبود» علامت بزنید.

هدف اصلی پذیرش: ظاهر جمع‌وجور و خوانا؛ حفظ تنظیمات قبلی؛ اینترنت عادی برای دامنه‌های بدون قانون و VPN برای سایت‌های منتخب؛ اجرای **Codex Desktop** با پراکسی مستقل؛ و امکان تنظیم مسیر عمومی ویندوز روی اینترنت عادی و بازگرداندن آن.

## ۱. آماده‌سازی و ثبت وضعیت اولیه

کارهای باز Codex و مرورگر را ذخیره کنید. برای تست‌های خودکار دسکتاپ، Netcontroll را از **منوی کنار ساعت → خروج** ببندید؛ بستن ضربدر پنجره لزوماً فرایند را متوقف نمی‌کند. VPN و تنظیمات شبکه را برای شروع، در وضعیت معمول خود نگه دارید.

در PowerShell معمولی این پوشهٔ شواهد را بسازید. مسیر آن موقت و بیرون از مخزن است:

```powershell
$ncEvidence = Join-Path $env:TEMP ('Netcontroll-acceptance-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $ncEvidence | Out-Null
$ncSettings = Join-Path $env:LOCALAPPDATA 'Netcontroll\settings.json'
if (Test-Path -LiteralPath $ncSettings) {
    Copy-Item -LiteralPath $ncSettings -Destination (Join-Path $ncEvidence 'settings-before.json')
}
Get-NetAdapter |
    Select-Object Name, InterfaceDescription, ifIndex, Status |
    Export-Csv -LiteralPath (Join-Path $ncEvidence 'adapters-before.csv') -NoTypeInformation -Encoding UTF8
Get-NetRoute -PolicyStore ActiveStore |
    Select-Object AddressFamily, DestinationPrefix, InterfaceIndex, InterfaceAlias, NextHop, RouteMetric, Protocol |
    Export-Csv -LiteralPath (Join-Path $ncEvidence 'routes-before.csv') -NoTypeInformation -Encoding UTF8
$ncEvidence
```

این خروجی‌ها نام رابط‌ها و آدرس‌های شبکهٔ شما را دارند؛ برای بررسی خودتان نگه دارید و وارد Git نکنید. اگر قبلاً قوانین IP یا مسیرهای شرکتی دارید، نام و مقصدشان را یادداشت کنید تا در آزمون بازگردانی بررسی شوند.

## ۲. ساخت و آزمون‌های خودکار

این فرمان‌ها را از ریشهٔ مخزن اجرا کنید. ساخت C# به **.NET Framework 4.8** و **Visual Studio Build Tools با MSBuild/Roslyn** نیاز دارد؛ آزمون افزونه به Node.js نیاز دارد. وجود این راهنما به معنی اجرای فرمان‌ها روی ویندوز شما نیست.

```powershell
powershell.exe -NoProfile -File .\build.ps1
node --test .\tests\chrome-policy.test.cjs
powershell.exe -NoProfile -File .\tests\CoreRouting.ps1
powershell.exe -NoProfile -File .\tests\DefaultDirect.Tests.ps1
powershell.exe -NoProfile -STA -File .\tests\Smoke.ps1
powershell.exe -NoProfile -STA -File .\tests\Desktop.ps1
```

هر فرمان باید بدون خطا تمام شود. پس از خطای build، تست‌های وابسته به `build\payload` یا `dist` را با خروجی قدیمی ادامه ندهید.

| آزمون | چه چیزی را بررسی می‌کند؟ | چه چیزی را ثابت نمی‌کند؟ | نتیجه |
| --- | --- | --- | --- |
| `chrome-policy.test.cjs` | اجرای PAC، پیش‌فرض Direct/VPN، تقدم دامنه، localhost، تغییر سایت، مالکیت پراکسی و قطع اتصال | نصب افزونه یا مسیر واقعی اینترنت | اجرا نشده |
| `CoreRouting.ps1` | کد واقعی مدل و API محلی، درخواست‌های معتبر/نامعتبر، تنظیمات و قرارداد اجرای برنامه | رفتار نسخهٔ نصب‌شدهٔ Codex یا درایور VPN | اجرا نشده |
| `DefaultDirect.Tests.ps1` | مالکیت مسیرها، تکرارپذیری، تعارض، بازیابی و IPv6 با فرمان‌های شبکهٔ شبیه‌سازی‌شده | تغییر واقعی جدول مسیر یا فایروال ویندوز | اجرا نشده |
| `Smoke.ps1` بدون گزینهٔ Live | محتوای بسته، API محلی، مدل و بارگذاری WPF | خروجی عمومی واقعی شبکه | اجرا نشده |
| `Desktop.ps1` | بازشدن executable واقعی، ورود به IPها، اسکن و نمایش نام‌های ذخیره‌شده | تمام صفحات، تمام DPIها یا ظاهر بدون نقص | اجرا نشده |

`Desktop.ps1` برنامه را برای آزمایش باز می‌کند و در پایان همان فرایند تست را می‌بندد. در زمان اجرای آن نمونهٔ دیگری از Netcontroll باز نباشد.

**آزمون اختیاری نصب:** `tests/InstallerLayout.ps1` ظاهر installer را در DPI فعلی می‌سنجد و نصب انجام نمی‌دهد. `tests/WindowsRoutes.ps1` مخصوص محیط آزمایشی پاک، PowerShell مدیر و OpenVPN فعال است؛ مسیر و فایروال واقعی را تغییر می‌دهد و روی لپ‌تاپی که تنظیمات فعال Netcontroll دارد، نباید به‌عنوان تست روزمره اجرا شود.

## ۵. سناریوی اصلی: ۵۰ دامنهٔ عادی و یک سایت VPN

### ۵.۱. آماده‌کردن حالت معکوس

۱. VPN را روشن کنید و در بالای برنامه، شناسایی رابط عادی و رابط VPN را بررسی کنید.

۲. در «مرورگر و دامنه‌ها»، پیش‌فرض مرورگر را **اینترنت عادی / VPN فقط برای انتخاب‌شده‌ها** انتخاب کنید. این انتخاب، `ChromeDefault = Direct` است؛ انتخاب پیش‌فرض مرورگر به‌تنهایی پیش‌فرض کل ویندوز را تغییر نمی‌دهد.

۳. افزونهٔ پروفایل روزمره را متصل کنید. وضعیت popup باید اعمال و تأیید قوانین را نشان دهد و برنامه نیز دریافت قوانین توسط آن پروفایل را تأیید کند. بازبودن پنجرهٔ Chrome بدون این تأیید کافی نیست.

۴. یک سایت واقعی نیازمند VPN را باز کنید، popup را باز کنید و **فقط VPN** را بزنید. ابتدا گزینهٔ زیردامنه‌ها خاموش باشد تا قانون فقط برای همان میزبان ساخته شود. سپس تب را با دکمهٔ popup تازه کنید.

۵. از فهرست واقعی خود، ۵۰ میزبان عادی را انتخاب کنید که قانون VPN یا قانون والد VPN ندارند. لازم نیست برای هرکدام قانون Direct بسازید؛ هدف آزمون، کارکرد پیش‌فرض Direct است. قواعد قبلی را برای این تست دسته‌جمعی حذف نکنید.

### ۵.۲. ثبت نتیجه

برای هر میزبان نتیجهٔ بازشدن و فعالیت اتصال تازه را ثبت کنید. گزارش فعالیت فقط آخرین ۱۲۰ اتصال را در حافظه نگه می‌دارد؛ ۵۰ سایت می‌توانند بسیار بیش از ۱۲۰ درخواست بسازند. بنابراین شواهد را در گروه‌های کوچک جمع کنید، نه فقط پس از بازکردن همهٔ سایت‌ها.

| مورد | انتظار | شاهد لازم | نتیجه |
| --- | --- | --- | --- |
| سایت منتخب VPN | اتصال تازه از مسیر VPN | زمان تازه، میزبان مربوط، حالت VPN و آدرس مبدأ رابط VPN در فعالیت؛ سایت نیز بارگذاری شود | اجرا نشده |
| هر یک از ۵۰ میزبان بدون قانون | مسیر Direct | ردیف اتصال مرتبط با آدرس مبدأ رابط عادی؛ نتیجهٔ بارگذاری همان سایت | اجرا نشده |
| قانون غیرفعال VPN | بازگشت به پیش‌فرض Direct یا قانون والد | مسیر مؤثر popup و اتصال تازه | اجرا نشده |
| قانون دقیق‌تر زیر دامنه | قانون دقیق‌تر برنده باشد | آزمون میزبان والد و فرزند جداگانه | اجرا نشده |
| حذف قانون اختصاصی از popup | فقط همان قانون حذف شود | نام‌های دیگر باقی بمانند؛ مسیر مؤثر به والد یا پیش‌فرض برگردد | اجرا نشده |
| تغییر سایت هنگام بازبودن popup | قانون برای صفحهٔ قدیمی ثبت نشود | پیام تغییر صفحه؛ بازکردن دوبارهٔ popup | اجرا نشده |
| `localhost` و صفحهٔ داخلی Chrome | قانون عمومی سایت ساخته نشود | کنترل مسیر غیرفعال و توضیح مناسب | اجرا نشده |

قالب پیشنهادی یادداشت هر سایت: `میزبان | قانون مؤثر | مسیر مورد انتظار | زمان آزمون | آدرس مبدأ مشاهده‌شده | نتیجهٔ بارگذاری`.

**مرز مهم سایت و تب:** قانون افزونه بر میزبان درخواست اعمال می‌شود. دو تب از یک دامنه در همان پروفایل، قانون مشترک دارند. یک صفحه ممکن است درخواست‌هایی به CDN یا سرویس ورود روی دامنه‌های دیگر بفرستد؛ قانون میزبان اصلی خودبه‌خود همهٔ آن دامنه‌ها را شامل نمی‌شود. ظاهر شدن ردیف VPN برای یک درخواست نیز اثبات نمی‌کند که همهٔ درخواست‌های آن صفحه VPN بوده‌اند.

### ۵.۳. جداسازی کامل یک گروه تب

از برنامه، **پنجرهٔ فقط VPN** را باز کنید و سایت وابسته به CDN یا چند سرویس را در همان پنجره امتحان کنید. پنجرهٔ **مستقیم** را نیز باز کنید و یک سایت عادی را آنجا امتحان کنید. این‌ها پروفایل‌های مستقل‌اند و ورودها، کوکی‌ها و تاریخچهٔ روزمره را به‌صورت خودکار به اشتراک نمی‌گذارند.

انتظار: اتصال‌های وب پنجرهٔ اول با منبع `Chrome · VPN` و پنجرهٔ دوم با `Chrome · Direct` ثبت شوند. تنظیم دامنه در Chrome روزمره نباید مسیر ثابت این پنجره‌ها را عوض کند. این روش، جداسازی یک **پنجره/پروفایل** است، نه مسیریابی مستقل دو تب هم‌دامنه داخل یک پروفایل.

## ۶. اندازه‌گیری اختیاری خروجی عمومی

این بخش فقط در صورتی اجرا شود که مایلید به یک سرویس عمومی نمایش IP درخواست بفرستید. سرویس مقصد IP عمومی اتصال شما را می‌بیند. Netcontroll پاسخ IP عمومی را در تنظیمات کاربر ذخیره نمی‌کند؛ فعالیت برنامه، میزبان و آدرس مبدأ محلی اتصال را موقتاً نگه می‌دارد. اگر گزینهٔ خودکار `Smoke.ps1 -Live` را اجرا کنید، خروجی سرویس در فایل‌های تست `build\smoke-*` نوشته می‌شود.

با Netcontroll باز و VPN متصل، در PowerShell معمولی اجرا کنید:

```powershell
curl.exe -4 --fail --silent --show-error --connect-timeout 5 --max-time 15 --noproxy netcontroll-no-bypass.invalid --proxy http://127.0.0.1:17835 "https://api.ipify.org/?format=json"
curl.exe -4 --fail --silent --show-error --connect-timeout 5 --max-time 15 --noproxy netcontroll-no-bypass.invalid --proxy http://127.0.0.1:17834 "https://api.ipify.org/?format=json"
```

فرمان اول از پراکسی پنجرهٔ مستقیم و فرمان دوم از پراکسی VPN استفاده می‌کند. مقدار غیرواقعی `--noproxy` عمداً باعث می‌شود تنظیم محیطی `NO_PROXY` این سرویس عمومی را دور نزند. برای هر فرمان، موفقیت HTTP، پاسخ IP و ردیف فعالیت هم‌زمان را با هم بررسی کنید. معمولاً IP خروجی دو مسیر متفاوت است؛ اگر برابر بود، با شواهد رابط و وضعیت VPN بررسی کنید و نتیجه را بدون دلیل «قبول» علامت نزنید.

برای آزمون خودکار زندهٔ موجود نیز می‌توان از این فرمان استفاده کرد؛ به Chrome نصب‌شده، مسیرهای Direct/VPN فعال و دسترسی به همان سرویس عمومی نیاز دارد:

```powershell
powershell.exe -NoProfile -STA -File .\tests\Smoke.ps1 -Live
```

## ۷. Codex Desktop: اجرا و مشاهدهٔ درخواست واقعی

این بخش دربارهٔ **برنامهٔ دسکتاپ Codex** است. وجود ابزار CLI با نام مشابه، معیار قبول این آزمون نیست.

۱. کارهای باز Codex را ذخیره کنید و از خود برنامه کاملاً خارج شوید. در صورت نیاز، فقط باقی‌ماندن فرایندها را بررسی کنید:

```powershell
Get-Process -Name Codex -ErrorAction SilentlyContinue | Select-Object Id, ProcessName, Path
```

۲. در بخش `Codex Desktop`، «تشخیص خودکار» را بزنید؛ اگر شناسایی نشد، فایل اجرایی واقعی نصب دسکتاپ را انتخاب کنید. میان‌بر وب، فایل CLI یا اجرای `codex` در ترمینال جایگزین این مرحله نیست.

۳. مسیر **فقط VPN** را انتخاب کنید و **اجرای Codex Desktop** را از Netcontroll بزنید. برنامه باید نمونهٔ تازه را با پراکسی اختصاصی `http://127.0.0.1:17833` راه‌اندازی کند.

۴. داخل Codex یک درخواست تازه و کوتاه بدون تغییر فایل، مانند پاسخ به «سلام»، ایجاد کنید. هم نتیجهٔ درخواست در خود Codex و هم **اتصال تازه با منبع `Codex`** را در Netcontroll بررسی کنید. ردیف فعالیت باید حالت VPN و آدرس مبدأ رابط VPN داشته باشد. اتصال قدیمی یا صرف بازشدن پنجره برای قبول کافی نیست.

۵. Codex را کامل ببندید، مسیر را Direct انتخاب کنید، دوباره از Netcontroll اجرا کنید و همین آزمون را با آدرس مبدأ رابط عادی تکرار کنید. در پایان حالت موردنظر خود را برگردانید.

| کنترل | معیار قبول | نتیجه |
| --- | --- | --- |
| انتخاب executable | نسخهٔ دسکتاپ واقعی انتخاب شده و مسیر قابل خواندن است | اجرا نشده |
| اجرای تازه | برنامه باز شود؛ نمونهٔ قبلی تنظیم تازه را نبلعد | اجرا نشده |
| درخواست واقعی روی VPN | درخواست پاسخ بگیرد و اتصال تازهٔ مرتبط با منبع Codex/حالت VPN دیده شود | اجرا نشده |
| درخواست واقعی روی Direct | درخواست پاسخ بگیرد و اتصال تازهٔ مرتبط با منبع Codex/حالت Direct دیده شود | اجرا نشده |
| بی‌اثر بودن تغییر پیش‌فرض مرورگر | Codex همچنان از مسیر مستقل خودش استفاده کند | اجرا نشده |
| حالت بدون اتصال مشاهده‌شده | UI موفقیت ساختگی نشان ندهد؛ پیام «هنوز اتصالی دیده نشده» یا خطا قابل مشاهده باشد | اجرا نشده |

پذیرش پراکسی به رفتار نسخهٔ Codex و فرایندهای داخلی آن وابسته است. مشاهدهٔ یک اتصال پس‌زمینه، به‌تنهایی عبور تمام درخواست‌های برنامه را ثابت نمی‌کند. اگر برنامه کار می‌کند ولی اتصال مرتبط در پراکسی دیده نمی‌شود، نتیجهٔ مسیریابی آن درخواست **تأیید نشده** است؛ حدس نزنید.

## ۸. حالت ویندوز: اینترنت عادی برای سایر برنامه‌ها

برای سناریوی «VPN روشن باشد؛ Codex از VPN و ترافیک عمومی ویندوز از اینترنت عادی»، دو بخش باید جداگانه تأیید شوند: پراکسی اختصاصی Codex و تنظیم **اینترنت عادی برای سایر برنامه‌های ویندوز** در نمای کلی.

### ۸.۱. فعال‌سازی و بررسی واقعی

۱. VPN را روشن نگه دارید. در نمای کلی، **فعال‌سازی اینترنت عادی** را بزنید و UAC ویندوز را تأیید کنید.

۲. متن «تنظیم ذخیره‌شده» را با گزارش **آخرین اعمال موفق مسیرها** مقایسه کنید. گزارش قدیمی، خطای سرویس یا تفاوت با تنظیم ذخیره‌شده، قبول نیست. خود گزارش موفق نیز آزمون دسترسی به اینترنت نیست.

۳. در PowerShell، مسیرهای متعلق به این قابلیت را بخوانید:

```powershell
Get-NetRoute -AddressFamily IPv4 -PolicyStore ActiveStore |
    Where-Object { $_.RouteMetric -eq 1732 -and $_.Protocol -eq 'NetMgmt' } |
    Sort-Object DestinationPrefix |
    Format-Table DestinationPrefix, InterfaceIndex, InterfaceAlias, NextHop, RouteMetric, Protocol

Get-Content -LiteralPath (Join-Path $env:ProgramFiles 'Netcontroll Routes\route-status.json') -Raw
Get-ScheduledTask -TaskName 'Netcontroll - IPv4 routes' |
    Select-Object TaskName, State
```

انتظار: چهار مسیر IPv4 برای `0.0.0.0/2`، `64.0.0.0/2`، `128.0.0.0/2` و `192.0.0.0/2` روی رابط فیزیکی منتخب و gateway آن وجود داشته باشند. مسیرهای اصلی VPN حذف نشده باشند. وظیفهٔ زمان‌بندی‌شده همچنان نام تاریخی «IPv4 routes» دارد، اما قابلیت تازهٔ IPv6 نیز از همین عامل مدیریت می‌شود.

۴. یک برنامه یا درخواست **بدون پراکسی** را امتحان کنید. با رضایت مرحلهٔ اندازه‌گیری عمومی، این فرمان، پراکسی‌های محیط را دور می‌زند و مسیر معمول ویندوز را می‌سنجد:

```powershell
curl.exe -4 --fail --silent --show-error --connect-timeout 5 --max-time 15 --noproxy "*" "https://api.ipify.org/?format=json"
```

خروجی باید با مسیر اینترنت عادی سازگار باشد. این درخواست مستقیماً از Windows می‌رود و نبودنش در تاریخچهٔ پراکسی Netcontroll طبیعی است. هم‌زمان، آزمون واقعی Codex در بخش قبل باید همچنان خروجی VPN داشته باشد.

### ۸.۲. بازخوانی شبکه و ماندگاری

در زمان مناسب برای قطع کوتاه اتصال، Wi-Fi را قطع و وصل کنید یا بین Wi-Fi و Ethernet جابه‌جا شوید. سپس گزارش سرویس و رابط مسیرهای `1732` را دوباره بررسی کنید. عامل در رخدادهای شبکه و به‌طور دوره‌ای هر دو دقیقه بازخوانی می‌کند؛ وضعیت گذار را با وضعیت نهایی یکسان ندانید.

برای اجرای دستی یک بازخوانی، در PowerShell **Run as administrator** می‌توانید از این فرمان استفاده کنید:

```powershell
Start-ScheduledTask -TaskName 'Netcontroll - IPv4 routes'
```

پس از چند ثانیه زمان `CheckedAtUtc` و جدول مسیر را دوباره بخوانید. یک بار بستن و بازکردن Netcontroll و یک بار راه‌اندازی مجدد ویندوز را نیز در زمان مناسب آزمایش کنید. باقی‌ماندن مسیرهای تأییدشده پس از خروج برنامه، رفتار سرویس سیستمی است؛ خروج از tray معادل غیرفعال‌کردن این حالت نیست.

### ۸.۳. بازگرداندن مسیر اصلی

در نمای کلی، **بازگشت به مسیر اصلی** را بزنید و UAC را تأیید کنید. انتظار:

- مسیرهای journalشدهٔ `/2` با metric `1732` حذف شوند.
- قواعد IPv6 مربوط به همین قابلیت حذف شوند.
- مسیرهای VPN، مسیرهای IP اختصاصی و قواعد نامرتبط با این قابلیت حفظ شوند.
- مسیر خروجی جدید طبق تنظیم معمول ویندوز/VPN انتخاب شود.

برای بازگردانی، فایل journal یا تمام مسیرهای ویندوز را دستی حذف نکنید. اگر تطبیق مالکیت یا تعارض گزارش شد، خطا و جدول مسیر را ثبت کنید؛ رفع آن با حذف گروهی مسیرهای دیگر قبول نیست.

## ۹. قطع VPN و IPv6

### قطع VPN؛ بدون fallback پنهان

با Netcontroll باز، VPN را قطع کنید و یک **اتصال تازه** از سایت VPN، پنجرهٔ فقط VPN و پراکسی Codex ایجاد کنید. انتظار این است که اتصال اجباری VPN خطا بدهد و خودکار به Direct تبدیل نشود. صفحهٔ cacheشده یا پاسخ قدیمی معیار نیست. می‌توان فرمان دوم بخش اندازه‌گیری عمومی را دوباره اجرا کرد؛ هر اجرای curl یک اتصال تازه می‌سازد.

در همان زمان، درخواست Direct باید با وجود اینترنت فیزیکی سالم همچنان قابل انجام باشد. پس از اتصال دوبارهٔ VPN، آزمون انتخابی را مجدداً اجرا کنید. نتیجه را همراه زمان، حالت و منبع اتصال ثبت کنید.

این الزام fail-closed مربوط به **اتصال‌هایی است که از پراکسی Netcontroll عبور می‌کنند**. برنامه یا فرایندی که پراکسی را نادیده می‌گیرد، صرفاً با انتخاب حالت VPN در UI تحت کنترل همه‌جانبه قرار نمی‌گیرد.

### IPv6 در حالت عادی ویندوز

| وضعیت واقعی شبکه | انتظار از حالت Windows Direct | شاهد | نتیجه |
| --- | --- | --- | --- |
| gateway فیزیکی IPv6 موجود است | چهار مسیر IPv6 با metric `1732` روی رابط فیزیکی ساخته شود | جدول IPv6؛ در صورت رضایت، آزمون عمومی IPv6 بدون پراکسی | اجرا نشده |
| gateway فیزیکی IPv6 موجود نیست و رابط VPN شناخته شده است | خروج IPv6 از رابط‌های VPN شناخته‌شده توسط قاعدهٔ این قابلیت محدود شود | قاعدهٔ `DefaultDirect-IPv6` و فیلتر رابط/آدرس آن | اجرا نشده |
| حالت Windows Direct غیرفعال شد | محدودیت IPv6 همین قابلیت برداشته شود | نبود قاعدهٔ مربوط، بدون حذف قواعد دیگر | اجرا نشده |

فرمان‌های خواندنی:

```powershell
Get-NetRoute -AddressFamily IPv6 -PolicyStore ActiveStore |
    Where-Object { $_.RouteMetric -eq 1732 } |
    Format-Table DestinationPrefix, InterfaceIndex, InterfaceAlias, NextHop, RouteMetric

Get-NetFirewallRule -Name 'Netcontroll.Routes.DefaultDirect-IPv6.*' -ErrorAction SilentlyContinue |
    Format-Table Name, Enabled, Direction, Action
Get-NetFirewallRule -Name 'Netcontroll.Routes.DefaultDirect-IPv6.*' -ErrorAction SilentlyContinue |
    Get-NetFirewallInterfaceFilter
Get-NetFirewallRule -Name 'Netcontroll.Routes.DefaultDirect-IPv6.*' -ErrorAction SilentlyContinue |
    Get-NetFirewallAddressFilter
```

بدون IPv6 قابل استفاده، آزمون اینترنت IPv6 را «قابل‌آزمون نبود» ثبت کنید. وجود قاعدهٔ فایروال به‌تنهایی اثبات دسترسی یا عدم دسترسی همهٔ برنامه‌ها نیست. پراکسی اجباری Direct/VPN فعلی از خروجی IPv4 استفاده می‌کند.

## ۱۰. محدوده‌های فنی که در نتیجه باید نوشته شوند

- **قانون دامنه، قانون تب نیست:** افزونهٔ Chrome بر میزبان درخواست در یک پروفایل تصمیم می‌گیرد. برای جداسازی گروهی از تب‌ها، پنجرهٔ مستقل استفاده کنید.
- **این نسخه درایور WFP یا کنترل اجباری تمام فرایندها ندارد:** پراکسی، گزینه‌های اجرای برنامه، مسیرهای Windows و قفل فایروال ابزارهای مجزا هستند. قفل فایروال مسیر تولید نمی‌کند؛ فقط می‌تواند خروج نامجاز را مسدود کند.
- **مسیرهای دقیق‌تر محفوظ‌اند:** مسیرهای میزبان، شبکهٔ محلی یا شرکتی می‌توانند بر مسیر عمومی `/2` مقدم باشند. مسیر هم‌طول متعارض باید خطای روشن بدهد، نه موفقیت ساختگی.
- **DNS مستقل است:** حل نام از تنظیمات ویندوز استفاده می‌کند؛ DNS، DNS over HTTPS یا رفتار VPN را فقط از روی ردیف TCP پراکسی تأیید نکنید.
- **Kill switch مستقل است:** Netcontroll آن را خاموش نمی‌کند. اگر VPN ترافیک فیزیکی را مسدود کرده باشد، «Direct» ممکن است قابل استفاده نباشد.
- **تغییر شبکه لحظه‌ای نیست:** بازخوانی عامل و ایجاد اتصال تازه لازم است. حالت Windows Direct، تضمین پیوستهٔ جداسازی همهٔ ترافیک در تمام لحظات reconnect نیست.
- **نشانی محلی با IP عمومی فرق دارد:** ستون مبدأ فعالیت، آدرس رابط محلی است؛ IP عمومی را فقط با آزمون خروجی مناسب بررسی کنید.

مرجع رفتار مرورگر: [Chrome Proxy API](https://developer.chrome.com/docs/extensions/reference/api/proxy)، [ورودی‌های PAC در Chromium](https://github.com/chromium/chromium/blob/main/net/docs/proxy.md)، و [محدودیت اندازهٔ popup](https://developer.chrome.com/docs/extensions/reference/api/action). مرجع ترتیب انتخاب مسیر: [Windows route prefix/metric](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-tcpip-interfaces-interface-routes-route-metric) و [Get-NetRoute](https://learn.microsoft.com/powershell/module/nettcpip/get-netroute).
