# Netcontroll 2.0

کنترل مسیر اتصال در **Windows 10/11 x64** با رابط فارسی و راست‌به‌چپ.

**توسعه‌دهنده: Peyman Arjmand — [peymanarjmand308@gmail.com](mailto:peymanarjmand308@gmail.com)**

## محیط جدید

نمای کلی شبکه، مرورگر و دامنه‌ها، **Codex Desktop**، Docker Desktop، سایر برنامه‌ها، سرورها، فعالیت اتصال‌ها و راهنما در یک سایدبار دسته‌بندی‌شده قرار دارند. رابط زغالی و نارنجی، ورودی‌های جمع‌وجور، ردیف‌های فشرده، فیلتر مسیر و جست‌وجو دارد. در پنجرهٔ کوچک، سایدبار به ریل آیکون تبدیل می‌شود. `Ctrl+F` جست‌وجوی بخش جاری را فعال می‌کند.

آمار رابط از قوانین و اتصال‌های مشاهده‌شدهٔ همین اجرا می‌آید. نشانی کنار آداپتور، IP **محلی** آن است؛ نمایش آن به‌تنهایی اثبات دسترسی به اینترنت یا IP عمومی نیست. گزارش اعمال مسیرهای ویندوز نیز از آزمایش واقعی اینترنت جداست.

## به‌روزرسانی روی لپ‌تاپ

اگر سورس پروژه را روی لپ‌تاپ دارید، PowerShell را در پوشهٔ پروژه باز کنید:

```powershell
git pull --ff-only origin main
powershell -NoProfile -ExecutionPolicy RemoteSigned -File .\update.ps1 -SkipPull
```

`update.ps1` برنامه را می‌سازد، از فایل قوانین موجود نسخهٔ پشتیبان می‌گیرد و نصب‌کننده را باز می‌کند. در نصب‌کننده «به‌روزرسانی برنامه» را بزنید. برای دفعات بعد کافی است:

```powershell
powershell -NoProfile -ExecutionPolicy RemoteSigned -File .\update.ps1
```

به‌روزرسانی روی `main` انجام می‌شود و در صورت وجود تغییر محلی یا ناتوانی در fast-forward متوقف می‌شود؛ فایل‌های محلی را بازنویسی نمی‌کند. `-BuildOnly` فقط فایل نصب را می‌سازد. برای سورس دریافت‌شده با ZIP از `-SkipPull` استفاده کنید.

**پیش‌نیاز ساخت:** Windows x64، .NET Framework 4.8 و Visual Studio Build Tools شامل MSBuild و کامپایلر C# Roslyn. این پروژه برای اجرا به Node، .NET جدید، NuGet یا سرویس ابری نیاز ندارد. Node فقط برای تست افزونه استفاده می‌شود. ساخت مستقیم:

```powershell
powershell -NoProfile -File .\build.ps1
Start-Process .\dist\Netcontroll-Setup.exe
```

اگر فایل نصب آمادهٔ همین نسخه را دارید، اجرای `Netcontroll-Setup.exe` کافی است و پیش‌نیازهای **ساخت** لازم نیست. نصب‌کننده نسخهٔ قبلی را در محل همان کاربر به‌روزرسانی می‌کند. قوانین، نام سرورها و پروفایل‌های مرورگر در محل جداگانه باقی می‌مانند. برنامه با بستن پنجره کنار ساعت می‌ماند؛ خروج کامل از منوی همان آیکون است.

پس از نصب:

1. در `chrome://extensions`، افزونهٔ Netcontroll را **Reload** کنید. فایل `popup.css` جدید باید همراه فایل‌های افزونه باشد؛ نصب‌کننده آن را کپی می‌کند.
2. اگر افزونه از پوشهٔ قدیمی سورس بارگذاری شده، از داخل برنامه «اتصال مرورگر» را بزنید و مسیر نصب‌شده را به‌عنوان Load unpacked انتخاب کنید؛ دو نسخهٔ هم‌زمان افزونه فعال نباشد.
3. popup افزونه را باز و «اتصال این پروفایل» را بزنید. تأیید دریافت قوانین در برنامه دیده می‌شود.
4. تب‌ها و اتصال‌های قدیمی را دوباره بارگذاری کنید. Codex Desktop را کامل ببندید و از صفحهٔ اختصاصی جدید اجرا کنید.

## سناریوی اول: چند سایت با VPN و بقیه با اینترنت عادی

در «مرورگر و دامنه‌ها» حالت **VPN فقط برای انتخاب‌شده‌ها** را انتخاب کنید. پیش‌فرض مرورگر «اینترنت عادی» می‌شود؛ برای هر سایت نیازمند VPN، یک قانون «فقط VPN» بسازید. می‌توانید مستقیماً در popup افزونه، مسیر سایت جاری را انتخاب کنید. نیازی به ثبت ده‌ها سایت مستقیم نیست.

- دقیق‌ترین قانون فعال اولویت دارد. قانون دقیق زیردامنه بر قانون دامنهٔ مادر مقدم است.
- گزینهٔ «زیردامنه‌ها» اختیاری است. popup به‌صورت پیش‌فرض فقط میزبان جاری را تغییر می‌دهد.
- «پیش‌فرض» در popup قانون همان میزبان را حذف می‌کند؛ ممکن است قانون دامنهٔ مادر همچنان اعمال شود.
- «مسیر سیستم» صریحاً از مسیر فعلی ویندوز پیروی می‌کند و معادل اینترنت فیزیکی نیست.
- در حالت Direct، درخواست‌های خارجی از پراکسی محلی عبور می‌کنند تا سوکت خروجی واقعاً به رابط فیزیکی مقید شود. `DIRECT` در PAC به‌تنهایی در سیستم دارای VPN، تضمین اینترنت عادی نیست.
- اتصال‌های جدید انتخاب‌شدهٔ VPN در نبود آداپتور VPN خطا می‌دهند؛ پراکسی برای آن‌ها به اینترنت عادی fallback نمی‌کند.

حالت معکوس، **اینترنت عادی فقط برای انتخاب‌شده‌ها**، نیز موجود است: پیش‌فرض VPN و استثناهای مستقیم. در ارتقا، فایل قدیمیِ فاقد `ChromeDefault` همان رفتار قبلی `System` را حفظ می‌کند. نصب کاملاً تازه با پیش‌فرض Direct شروع می‌شود. حالت ویندوز هرگز خودکار فعال نمی‌شود.

### تب مستقل و دامنه یکسان

Chrome تنظیم پراکسی را در سطح **پروفایل** اعمال می‌کند؛ PAC فقط URL و host درخواست را می‌گیرد. قانون دامنه بین تب‌های همان میزبان مشترک است. برای جداسازی واقعی یک گروه تب، از **پنجرهٔ VPN** یا **پنجرهٔ مستقیم** در Netcontroll استفاده کنید. هرکدام پروفایل و پراکسی ثابت جدا دارد؛ درخواست‌های HTTP/HTTPS و WebSocket همان پروفایل، از جمله CDNهای سایت، از مسیر انتخابی عبور می‌کنند.

این پنجره‌ها ورودها، افزونه‌ها و داده‌های مستقل دارند. تب موجود را نمی‌توان با حفظ نشست پروفایل روزمره به پروفایل دیگر تبدیل کرد؛ نشانی سایت را در پنجرهٔ موردنظر باز کنید. در پروفایل روزمره، CDN و میزبان ورود متفاوت به قانون مناسب خود نیاز دارد. localhost از پراکسی مرورگر عبور نمی‌کند. DNS از حل‌کنندهٔ ویندوز استفاده می‌کند؛ پراکسی HTTP پوشش عمومی UDP/WebRTC نیست.

## سناریوی دوم: Codex Desktop با VPN و مسیر عمومی ویندوز مستقیم

این پروفایل برای **اپلیکیشن Codex Desktop** است؛ executable خط فرمان به‌عنوان برنامهٔ دسکتاپ انتخاب نمی‌شود.

1. VPN خود را روشن کنید.
2. در «نمای کلی»، **اینترنت عادی برای سایر برنامه‌های ویندوز** را فعال کنید و درخواست مدیر ویندوز را تأیید کنید.
3. در «Codex Desktop»، مسیر **فقط VPN** را انتخاب کنید.
4. «تشخیص خودکار» را بزنید؛ یا `Codex.exe` اصلی پوشهٔ نصب دسکتاپ را انتخاب کنید. نصب معمولی و مسیر بستهٔ Store بررسی می‌شود؛ مجوز پوشهٔ WindowsApps تغییر نمی‌کند.
5. Codex را کامل ببندید و از **اجرای Codex Desktop** داخل Netcontroll باز کنید.
6. یک درخواست تازه در Codex انجام دهید و «آخرین اتصال مشاهده‌شده» یا فیلتر Codex در فعالیت اتصال‌ها را بررسی کنید.

پراکسی اختصاصی Codex برابر `http://127.0.0.1:17833` است. اجرای تازه، متغیرهای پراکسی HTTP/HTTPS و تنظیم Chromium را می‌گیرد. این راه‌اندازی، پراکسی سراسری ویندوز یا تنظیمات دائمی Codex را تغییر نمی‌دهد. نسخهٔ از قبل باز ممکن است گزینه‌های راه‌اندازی جدید را نپذیرد. پذیرفتن پراکسی در فرایندهای فرعی/پلاگین‌ها باید در نسخهٔ نصب‌شده آزمایش شود؛ مشاهدهٔ اتصال از شروع موفق برنامه مهم‌تر است. [رفع اشکال Codex Desktop](docs/CodexDesktop-Troubleshooting.fa.md) جزئیات را توضیح می‌دهد.

### محدودهٔ حالت ویندوز و بازگردانی

این گزینه مسیر عمومی **اتصال‌های جدید** ویندوز را به Wi-Fi/Ethernet ترجیح می‌دهد. مسیرهای VPN حذف نمی‌شوند تا پراکسی‌های انتخاب‌شده همچنان به رابط VPN متصل شوند. چهار مسیر موقت IPv4 با پیشوند `/2` و مالکیت ثبت‌شده ساخته می‌شود؛ برای IPv6 دارای دروازهٔ فیزیکی نیز مسیر جدا ساخته می‌شود. اگر مسیر فیزیکی IPv6 موجود نباشد، یک قاعدهٔ فایروال متعلق به Netcontroll از استفادهٔ IPv6 روی آداپتور VPN جلوگیری می‌کند؛ پراکسی‌های صریح برنامه از IPv4 استفاده می‌کنند.

- مسیرهای اختصاصی دقیق‌تر، مانند قوانین IP یا شبکهٔ سازمانی، همچنان اولویت دارند. مسیر `/2` متعارض رد می‌شود و به مالکیت برنامه درنمی‌آید.
- این قابلیت درایور WFP برای رهگیری بی‌قیدوشرط تمام ترافیک هر فرایند نیست. برنامهٔ منتخب باید از پراکسی اختصاصی استفاده کند.
- Kill switch مستقل VPN می‌تواند دسترسی مستقیم را مسدود کند. DNS و DNS اختصاصی VPN توسط این گزینه بازنویسی نمی‌شوند.
- تغییر آداپتور/شبکه با تأخیر رویداد و حداکثر چرخهٔ دو دقیقه‌ای سرویس بازبینی می‌شود؛ اتصال‌های باز ممکن است نیازمند راه‌اندازی مجدد باشند.
- وضعیت آخرین اعمال، خطا، قدیمی بودن گزارش و اختلاف آن با تنظیم ذخیره‌شده در نمای کلی نمایش داده می‌شود. موفقیت اعمال، آزمون دسترسی عمومی اینترنت نیست.

برای لغو، **بازگشت به مسیر اصلی** را بزنید و UAC را تأیید کنید. فقط مسیرها و قواعد تحت مالکیت Netcontroll حذف می‌شوند؛ مسیر خارجی یا مسیری که metric/protocol آن تغییر کرده حذف نمی‌شود. حذف نرم‌افزار نیز پاک‌سازی را انجام می‌دهد. ابزار بازیابی دستی، در PowerShell مدیر:

```powershell
& "$env:ProgramFiles\Netcontroll Routes\Routes.ps1" -Action Remove
```

این دستور تمام مدیریت IP، قواعد فایروال و حالت پیش‌فرض متعلق به Netcontroll را برمی‌دارد؛ برای خاموش‌کردن فقط حالت عمومی از دکمهٔ برنامه استفاده کنید.

## Docker، سایر برنامه‌ها و IP

| بخش | رفتار |
|---|---|
| Docker Desktop | یک بار `http://127.0.0.1:17832` را در تنظیمات پراکسی HTTP و HTTPS مناسب Docker وارد کنید. سپس مسیر را در Netcontroll انتخاب کنید. آزمون دانلود، هم exit code و هم مشاهدهٔ اتصال رجیستری در پراکسی را بررسی می‌کند. |
| سایر برنامه‌ها | EXE و مسیر دلخواه را ثبت کنید. هر برنامه یک پورت `17900…17999` می‌گیرد. برنامه را از همین صفحه اجرا کنید یا نشانی پراکسی را داخل تنظیمات خودش بگذارید. برنامهٔ ناسازگار با پراکسی با انتخاب گزینهٔ رابط الزاماً مسیریابی نمی‌شود. |
| قفل فایروال برنامه | خروج فایل اجرایی روی رابط مخالف را محدود می‌کند؛ موتور تغییر مسیر نیست. فرایند فرعی به قانون خودش نیاز دارد. |
| سرورها و IP | IPv4 و نام سرور را ذخیره کنید. تغییر مسیر در سطح ویندوز و تمام پورت‌ها با UAC انجام می‌شود. اسکن، نام‌گذاری، مدیریت مسیرهای قبلی و حذف مبتنی بر snapshot حفظ شده‌اند. |
| فعالیت اتصال‌ها | آخرین ۱۲۰ اتصال محلی در حافظه، همراه با مقصد، منبع، مسیر، نتیجه و IP خروجی محلی. گواهی TLS جدید نصب نمی‌شود و محتوای HTTPS رمزگشایی نمی‌شود. |

## پورت‌ها و فایل‌های تنظیم

| کاربرد | پورت loopback |
|---|---|
| Chrome با قوانین دامنه | 17831 |
| Docker Desktop | 17832 |
| Codex Desktop | 17833 |
| پنجرهٔ مستقل VPN | 17834 |
| پنجرهٔ مستقل مستقیم | 17835 |
| برنامه‌های کاربر | 17900 تا 17999 |

تنظیمات شخصی: `%LOCALAPPDATA%\Netcontroll\settings.json`. نصب برنامه: `%LOCALAPPDATA%\Programs\Netcontroll`. داده‌های مدیریتی ویندوز: `%ProgramFiles%\Netcontroll Routes`. هیچ فایل تنظیم شخصی، مرورگر، کلید یا خروجی ساخت وارد Git نمی‌شود.

## آزمون‌ها

```powershell
node --test tests/chrome-policy.test.cjs
powershell -NoProfile -File tests/CoreRouting.ps1
powershell -NoProfile -File tests/DefaultDirect.Tests.ps1
powershell -NoProfile -STA -File tests/Smoke.ps1
powershell -NoProfile -STA -File tests/Desktop.ps1
```

سه مورد اول رفتار افزونه، هستهٔ پراکسی و مدیریت بازگردانی مسیرها را بررسی می‌کنند؛ تست `DefaultDirect.Tests.ps1` تمام cmdletهای شبکه را شبیه‌سازی می‌کند و شبکهٔ واقعی را تغییر نمی‌دهد. تست‌های WPF به ویندوز و بستهٔ ساخته‌شده نیاز دارند. تست قدیمی `WindowsRoutes.ps1` تغییر واقعی مسیر دارد و فقط روی محیط آزمایشی فاقد تنظیم فعال Netcontroll اجرا شود. برای تست عملی روی لپ‌تاپ از [راهنمای پذیرش ویندوز](docs/ACCEPTANCE.fa.md) استفاده کنید.

**GitHub Actions برای ساخت یا تست این تغییرات استفاده نمی‌شود.** فرمان‌های ساخت و تست در محیط محلی اجرا می‌شوند.

## مبنای فنی

- [Chrome proxy API](https://developer.chrome.com/docs/extensions/reference/api/proxy): محدودهٔ پروفایل و ورودی URL/host در PAC.
- [Electron proxy switches](https://www.electronjs.org/docs/latest/api/command-line-switches): پراکسی HTTP، HTTPS و WebSocket برای نمونهٔ تازه.
- [Windows IP_UNICAST_IF](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options): انتخاب رابط خروجی IPv4 برای سوکت.
- [Windows route metric](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-tcpip-interfaces-interface-routes-route-metric): اولویت پیشوند و سپس مجموع هزینهٔ مسیر و رابط.
